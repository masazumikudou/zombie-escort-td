# 交戦地レシピ（型カタログ）v0.1

**この文書の役割**: ステージ設計を「毎回ゼロから配置を考える」から「型を選んで刺す」に変えるための基礎資料。ここに書かれているのは、シム実測で裏が取れた事実と、小松の設計判断のみ。推測は書かない。

**作成日**: 2026-07-26

---

## 0. 基本の考え方

ステージの難しさは、交戦地1箇所の中身ではなく **交戦地をいくつ、どれだけ詰めて並べるか** で作る。1箇所あたりの上限は敵4体（鳥のみ例外）。

型は「交戦地1箇所で起きること」の単位。MAPや導線が変わっても、型の中身は変わらない。

**型を選ぶ前に §0.5 の禁止事項を通すこと。**
型カタログは「どう配置すれば成立するか」を出すが、
禁止事項に触れている盤面はそもそも型では救えない。

---

## 0.5 禁止事項（設計前チェックリスト）

型を選ぶ前に、まずここを通すこと。
**以下はいずれも、タワーの数や敵の体数では解決できない。**
数字の調整ではなく、置く場所そのものを変える必要がある。

| # | 禁止事項 | 詳細 |
|---|---|---|
| 1 | スタート直後・別導線の入口に敵を置かない | §2-5 |
| 2 | 敵を護衛のpath上に置かない | §8-7 |
| 3 | 護衛がGから5マス以内のときGから湧かせない | §8-4 |
| 4 | triggerは交戦させたい区間の中に置く | §8-6 |
| 5 | キックボードはGから固定で出す | §8-1 |
| 6 | Yの枝はY地点から4.5マス以内に収める | §9-6 |
| 7 | Y地点の周囲、各枝に届く位置にbuildSpotを置く | §9-6 |

### 1. スタート直後・別導線の入口に敵を置かない

プレイヤーには「スタート→盤面を見回す→展開を組み立てる」
の3段が必要。この時間がゼロだと理不尽になる。

**1人目だけでなく、導線が変わる家族すべてに適用する。**
別導線に入った瞬間、その道は初見になる。

詳細は §2-5。

### 2. 敵を護衛のpath上に置かない

護衛が通るセルそのものに敵を置くと、ゼロ距離で接触する。
タワーが撃ち始めてから1秒以内に殴られ始めるため、
**何基置いても被弾を止められない。**

実測（stage_test_06）: 警察がmomのpath上にあり45dmg被弾。
タワーを1基追加しても被弾は1ダメージも変わらなかった。
スポーンを3マス後退させることで解決。

### 3. 護衛がGから5マス以内のときGから湧かせない

湧いた直後に被弾が始まり、2秒の無敵すら消化されない。
**理不尽というより「無意味」——プレイヤーの判断が結果に反映されない。**

詳細は §8-4（この境界値は暫定）。

### 4. triggerは交戦させたい区間の中に置く

区間の範囲外に `atWpIdx` を置くと、湧いた直後に区間が終了し
onExit の retreat で敵が全部退場する。
**「倒せず殴られず消える」＝すり抜け扱いになる。**

### 5. キックボードはGから固定で出す

護衛の至近にtriggerで湧かせると、スポーン後2秒の無敵が
まるごと効いてプレイヤーの備えが無効化される（§2-6）。
Gから出せば走ってくる間に2秒が消化され、
かつ出る場所が固定されるので学習できる（§8-1）。

### この章の更新ルール

**「数字をいじっても直らなかった」問題が出るたびに、ここへ追加する。**
体数・間隔・基数の調整で解決した問題は、ここには入らない。

現在は単体の型から得られた5項目のみ。
混戦（重なり型）は未検証で、実ステージでの実測から
新しい禁止事項が出る可能性が高い。

## 1. 確定した計算式（実測済み）

### 1-1. 撃破時間

```
撃破時間 ＝ (発数 − 1) × 連射間隔 ＋ 0.3秒
発数 ＝ ceil(敵HP ÷ タワーの攻撃力)
```

**0.3秒は弾が飛ぶ時間。1発目に待ち時間はない**（敵が交戦対象になった瞬間に撃つ）。

検証: サラリーマン2発（実測1.05秒）／デブ6発（実測4.3秒）。発数が3倍違っても一致。

### 1-2. 交戦時間

```
交戦時間 ＝ (450 − 85) ÷ (護衛speed + 敵speed)
```

護衛範囲円は450pxだが、**ゾンビは85px手前から攻撃を届かせる**ため、実際に使えるのは365px分。

検証: サラリーマン(speed50)で3.65秒／デブ(speed25)で4.85秒。速度が倍違っても一致。

### 1-3. normalタワー基準値

| 項目 | 値 |
|---|---|
| 攻撃力 | 50 |
| 連射間隔 | 0.8秒 |
| 射程 | 250px |
| 費用 | 100G |

## 2. 確定した法則

### 2-1. すり抜けた敵の扱いは、速度差で決まる

```
敵speed ＜ 護衛speed → すれ違いざまに数回殴られて終わり（振り切れる）
敵speed ＞ 護衛speed → 護衛が死ぬまで殴られ続ける
```

検証: サラリーマン(50)・デブ(25)は数回で終了。キックボード(90)は8回殴り続けて護衛死亡。

**含意**: キックボード(90)・鳥(70)は「取り逃がしたら追いかけてくる敵」。ただし護衛を追って前進するため、**進行方向前方に置いたタワーが保険として機能する**。

護衛speed一覧: dad50 / mom65 / son70 / grandma35 / cat75

### 2-2. 敵を出す間隔が、タワーの連射間隔より広いと余裕が生まれる

タワーは0.8秒に1発しか撃てない。**敵が0.8秒以上の間隔で来ると、タワーは待ち時間が発生せず順番に処理できてしまう。**

検証（鳥8体・normal1基・同一条件）:

| 出す間隔 | 結果 |
|---|---|
| 0.8秒 | HP残100% / CLOSE_CALL 0回（余裕） |
| 0.1秒 | HP残90% / CLOSE_CALL 3回（ギリギリ） |

**含意**: 型の難易度は「敵の数」ではなく「**密度**」で決まる。同じ数でも間隔で別物になる。型には必ず出す間隔を書くこと。

### 2-3. タワーは道から150px以内に置く

射程250pxのnormalの場合:

| 道からの距離 | 撃てる時間 |
|---|---|
| 0〜100px | フル性能 |
| 150px | 約9割 |
| 200px | 約7割 |
| 225px以上 | 実質使用不可 |

**射程の6割より近くに置く**が目安。

### 2-4. 交戦地が近いと、タワー1基で両方カバーできる

2つの交戦地の中間にnormalを1基置いた場合:

| 交戦地の間隔 | 効果 |
|---|---|
| 4マス以内 | **両方フルカバー**（1基で2基分の仕事） |
| 5マス | 約9割 |
| 6マス | 約7割 |
| 7マス以上 | 半分以下 |

sniper(射程350)なら6マスまで両取り可能。**sniperの存在理由は単体性能ではなく、離れた2箇所を1基で見られること。**

**含意**:
- 交戦地を**5マス以上離せば独立**して扱える
- **4マス以内なら連結パターンとして1個にまとめて解く**必要がある
- 間隔4マス＝「真ん中に1基」が正解／6マス＝「それぞれに置く」が正解。**同じ敵数でも間隔で正解が変わる**。間違えても7割は働くため、上手い人だけが得をする構造になる

### 2-5. 最初の直線には敵を配置しない（実機で確定・2026-07-27）

ジェットコースターの最初の登りにあたる区間を必ず作る。ここを過ぎたら
いろんな展開が待ち受けている、という構造にする。

**発見の経緯**: stage_test_06の実機プレイで、dad区間の開幕が理不尽に
きつかった。スタート(0,4)と同じ一直線上、4マス先にサラリーマン3体を
置いていたため、歩き出して2秒で交戦が始まった（護衛範囲円450px＝4.5マス）。
被弾したが死亡はしていない。

**理不尽である理由**: プレイヤーは
「スタート→全体を見回す→なんとなく展開を組み立てる」
の3段を踏む必要がある。この時間がゼロだと、思考が整っておらず盤面も
見えていない状態で交戦が始まる。

**シムでは検出できない**: §4.6の猶予計算は「敵が範囲円に入ってから
護衛が最接近するまで」を測るが、**プレイヤーが盤面を読みタワーを建てる
時間を1秒も見込んでいない**。シムはタワーが最初から建っている前提で
動くため、開幕直後の交戦地は「猶予が長すぎる案山子」として計算される。
実際にはプレイヤーにとって猶予ゼロである。§3.7「CLOSE_CALLはシムで
測れない」と同型の、もう一段深い問題。

#### 適用範囲: 導線が変わる家族すべて

1人目だけではない。**導線が変われば焦る。ルートが違うから。**

プレイヤーが把握しているのは「盤面」ではなく
**「前の家族が通ったルート」だけ**である。別導線に入った瞬間、
その道は初見になる。

| | 初見の道 | 登りが必要か |
|---|---|---|
| 1人目 | 全部 | **必要** |
| 別導線の家族 | その導線の全部 | **必要** |
| 同一導線の後続 | なし | 不要 |

#### 関連する2つのルール

厳密には別のルールだが、実運用ではセットで扱う。

| | 内容 | 目的 |
|---|---|---|
| ルール1 | 最初の直線には敵を置かない | 考える時間を与える |
| ルール2 | 導線は最低1回は曲げる | 一本道は読みが要らない |
| ルール3 | 登り区間には、最初の交戦地に届くbuildSpotを置く | 見えているのに手が出せない状態を防ぐ |

ルール1だけを守ってルール3を落とすと、「見る時間はあるが何もできない」
区間になり、ルール1が無意味になる。登り区間は
**敵がいない場所であると同時に、最初の交戦地を撃てるspotが並ぶ場所**
でなければならない。normal射程250px＝2.5マスのため、曲がり角の手前
2マス前後にspotがあれば角の敵を撃てる。

#### 設計上の副作用

導線を分けるたびに、緩衝地帯を1つ作らされる。A/B導線は
「別導線＝遺産が効かない＝難しい」という難易度レバー（§3.6）である
と同時に、**敵を置けない区間を増やす**。導線を細かく分けるほど
ステージは間延びする。「濃さ」を優先する最終面では特に注意すること。

### 2-6. スポーン後2秒は無敵（実測・2026-07-27）

**実機ではゾンビはスポーン後2秒間タワーに狙われない。** Zombie.jsが全ゾンビに
`_spawnTimer = 2000` を設定し、Tower.jsのターゲット選定5箇所すべてに
除外ガードが入っている。護衛範囲円と同種の「開幕スナイプ防止」機構。

**撃破時間の式に、この2秒は入っていない。** §1-1の式は交戦が始まってからの
時間を表すもので、trigger型ではその手前に2秒が乗る。

#### 効くのはtrigger型だけ

initial型はスポーンがt=0なので、護衛が来る頃には2秒はとっくに消化済み。
**2秒の無敵と護衛範囲円450pxが同じ役割を果たす**ため、スポーン地点が
護衛から離れていれば影響がない。

**問題になるのは「タワーの至近に、速い敵を、triggerで湧かせる」場合だけ。**
このときタワーは2秒間まったく手出しできず、その間に敵は
`敵speed × 2秒` だけ護衛へ近づく（キックボードなら180px＝1.8マス）。

| 敵 | speed | 2秒で進む距離 |
|---|---|---|
| キックボード | 90 | 180px |
| 鳥 | 70 | 140px |
| サラリーマン・作業員・警察 | 50 | 100px |
| デブ | 25 | 50px |

#### キックボードの評価が逆転した

§3.5では「normal1基で4体まで余裕・体数の型が成立しない」としていたが、
これは撃破0.3秒の前提。**実際は2.3秒かかる。**

stage_test_06の実機テストで、キックボード3体が単独で135dmgを叩き出した
（他の敵種の被弾は45dmgのみ）。HP50・1発で死ぬ最弱の敵が、
**2秒の無敵とspeed90だけで全被害を出した。**

**火力を倍にしても被害は1ダメージも減らなかった。** 1発で死ぬ敵に対しては
基数を増やしても意味がなく、「2秒撃てない」事実だけが被害を決める。
**配置では解けない問題である。**

## 3. 型の書き方

型には以下を書く。**必要なタワー基数は書かない**（使うタワーと護衛によって変わるため、その場で計算する）。

```
【型名】
　敵の構成 ： 種類と数
　出す間隔 ： 秒
　来る向き ： 正面／横／背後
```

必要基数の計算:

```
必要基数 ＝ ceil(体数 × 撃破時間 ÷ 交戦時間)
```

## 3.5 initial型カタログ（確定・2026-07-26）

### 対象と前提

- **initial型**＝護衛の進路上に敵が最初から立って待機している交戦地。護衛範囲円に入るまで敵は静止している
- まっすぐな道・正面衝突を前提とする
- タワーは **normal（100G）のみ**で計算
- 数値は §1 の確定式から算出

```
必要基数 ＝ ceil(体数 × 撃破時間 ÷ 交戦時間)
余裕率　 ＝ (交戦時間 × 基数) ÷ (体数 × 撃破時間)
```

**採用基準**: 余裕率 1.05〜1.60。この帯を外れるものは型として使わない。

> **注記**: この採用基準は暫定値。実測の裏付けは「余裕率1.13でCLOSE_CALLが1回発生」の1件のみ。実機プレイでの手応えと照合して確定させること。

**この2種を体数の型として扱わないこと。**

### 使い方

1. 交戦地に置きたい敵と体数を決める
2. **その区間を通る護衛**の列を見て、必要基数を読む
3. 余裕率が1.05〜1.60（★）でなければ、体数を変えるか敵を変える

**同一交戦地を複数の護衛が通る場合は、最も基数を要する護衛に合わせる**か、あるいは意図的に不足させて後続の難易度を上げる。

### この表の限界

- **normal専用**。sniperは単体性能ではnormal3基に大きく劣る（同額300Gで処理体数が3〜7倍の差）ため、**離れた2箇所を1基で見る用途以外では使わない**（§2-4）
- **cannon / punch は現状使い道がない**。cannonは1基ならnormalより速いが、2基以上になるとダメージが余りnormalに逆転される（実測: デブ2体をnormal2基が19450msで、cannon2基が20100msで撃破。費用は200Gと400G）。punchは射程100pxのため道の上にしか置けず、連射2.0秒が遅すぎて単体では機能しない。**両者は数値の見直しが必要な課題として残る**
- **ice は型の対象外**。spec06の設計原則どおり、三層検証はice抜きで成立させる。iceはクリアを容易にする救済手段であり、型の必要構成には含めない
- 敵種を混ぜた型（重なり型）は未検証

## 3.6 猶予ベースの必要基数（実ステージで検証済み・2026-07-26）

### §3.5の数字をそのまま使ってはいけない

§3.5の表は**まっすぐな道・正面衝突**を前提に算出したもの。この条件は**交戦時間が最も短い**（＝タワーにとって最も不利）ため、実際のマップに当てはめると**過剰になる**。

```
§3.5の表 ＝ 最悪ケース。これだけあれば絶対に守れるという最低保証
実際に必要な数 ＝ その地点の猶予から計算する
```

### 計算式

```
必要基数 ＝ ceil(体数 × 撃破時間 ÷ その地点の猶予)
余裕率　 ＝ (猶予 × 基数) ÷ (体数 × 撃破時間)
```

**猶予は導線とescort speedだけで決まる**（§4.6・spec06参照）。敵にもタワーにも依存しないため、導線を引いた時点で全地点について算出できる。

**狙う余裕率は 1.0〜1.3。**

### 検証: 18×18・3人リレー（dad A導線 / mom B導線 / son A導線）

交戦地9箇所・敵46体のステージで、同じ配置を2通りの基数で比較した。

| | §3.5の表通り | **猶予から再計算** |
|---|---|---|
| 基数 | 18基（1800G） | **12基（1200G）** |
| 生還 | 3/3 | 3/3 |
| HP残 | 100% | 100%（momのみ40被弾） |
| CLOSE_CALL | 1回 | **3回** |
| 最接近 | 144px | **1px** |

**6基（600G）削っても成立し、かつ緊張が生まれた。**

### 危険地点の事前予測に成功した

猶予から余裕率を算出すると、最も低い3箇所は以下だった。

| 交戦地 | 余裕率 |
|---|---|
| F ゴール手前（警察2体） | 1.06 |
| J 下の横道左（デブ2体・mom専用） | 1.07 |
| I 左縦道下（作業員3体・mom専用） | 1.09 |

**シムでCLOSE_CALLが発生したのは、この3箇所すべて。**被弾もJで発生した。

**計算だけで「どこが危ないか」を事前に特定できることが実証された。**シムでの試行錯誤を経ずに、一発でギリギリの盤面が作れる。

### 家族差も設計通りに再現された

被弾したのは**mom（speed65・B導線）のみ**。

- momは速いため交戦時間が短い（§1-2）
- B導線は他の家族と重ならないため、**遺産タワーが1基も効かない**

「速い家族が別導線で苦戦する」という設計意図が、そのまま数値に出た。

### 隣接タワーの助力を数え忘れると偏る

12基構成で被弾したJは、**周囲に他のタワーが1基もない孤立した交戦地**だった。

一方、被弾しなかったF・Iは、計算上は1基でも、実際には**隣の交戦地のタワーが射程内に入って手伝っていた**（§2-4の4マス以内カバー）。

**交戦地ごとに独立して基数を出すと、孤立した地点だけが不足する。**Jに1基足して13基（1300G）にしたところ、全員100%・被弾ゼロになった。

| 資金 | 結果 |
|---|---|
| 1200G（12基） | momが40被弾（100%割れ） |
| **1300G（13基）** | **全員100%・被弾ゼロ** |

**このステージの「良100%配置」は1300G**（spec06 §7の絶対条件を充足）。

### 設計手順

1. 導線を引く（小松）
2. 猶予マップを計算する ← 敵もタワーもまだ置かない
3. 交戦地を置く（余裕率が破綻する地点を避ける）
4. 必要基数 ＝ 体数 × 撃破時間 ÷ その地点の猶予
5. 孤立した交戦地には隣接タワーの助力がないため1基上乗せする
6. 余裕率1.0〜1.3を狙う

## 3.7 CLOSE_CALLはシムで測れない（確定）

### 理由

シムでのタワー配置は、**指定しなければ全て開幕（t=0）に建つ**。この状態でのCLOSE_CALLは「予習を完璧に済ませた人が、最初から全部建てた場合」の数字であり、**実際のプレイとは別物**。

実際のプレイでは、プレイヤーは敵の起動を見てから建てる。**同じ配置でも、建てるタイミングが違うだけでCLOSE_CALLは大きく変わる。**

### 検証: 建設タイミングを遅らせた場合

同じ13基の配置で、建設時刻だけを変えて比較した。

| 建設タイミング | 生還 | CLOSE_CALL | 判定 |
|---|---|---|---|
| 開幕に全部 | 3/3 | 2回 | CLEAR |
| 起動の0.5秒前 | 3/3 | 3回 | CLEAR |
| **起動の3秒後** | **0/3** | **7回** | **GAMEOVER** |

**0.5秒前は開幕と実質同じ**だった。タワーは敵が起動するまで撃たないため、それより前に建てても撃ち始める時刻は変わらない。

**3秒後は全滅した。**ただしこれは遅延そのものの効果ではなく、後述の連鎖崩壊による。

### 3秒遅延テストが測定にならなかった理由

シムの建設指定は**実時間（絶対時刻）**でしか書けない。

dadがt=29秒で死亡した結果、momの出番が予定より27秒早く始まったが、**タワーの建設時刻は元のまま**だった。momは自分の区間のタワーが1基も建っていない状態で歩き、そのまま死亡した。

実際のプレイではプレイヤーが護衛の現在地を見て建てるため、こうした「遅刻」は起きない。**時刻固定という仕組みの限界**であり、遅延プレイの再現には使えない。

### 結論

| | 測るもの |
|---|---|
| **シム** | 良100%配置が存在するか／どの地点の余裕率が最も低いか |
| **実機** | CLOSE_CALL・面白さ |

**CLOSE_CALLをシムの合否判定に使わない。**
ただし0回は例外で、「何も起きていない」の証明として
設計NG判定に使える（人格章の運用ルール1）。

1回以上の回数は、シム・実機を問わず合否に使わない。
3秒遅延テストでCLOSE_CALL 7回が出たが、これは全滅時の数字である。
**回数だけでは「ギリギリ」と「崩壊」を区別できない。**
見るべきは回数ではなく発生箇所数（人格章の運用ルール3）。

### 副次的に判明したこと

**1人の護衛が死ぬと、後続に連鎖する。**

区間境界のretreatは敵をリセットするが、**タワーと資金はリセットされない**。前の家族が早く死ぬと、後続は想定より少ない遺産と資金で始まることになる。

これは仕様として正しい挙動だが、**難易度設計上は「1人目の失敗が全体を崩す」構造**であることを認識しておく必要がある。

## 4. 鳥は別枠

鳥は他の敵と根本的に性質が異なるため、通常の型カタログとは分けて扱う。

### 4-1. 鳥の性質（確定）

- **「事前に対空を備えていたか」だけを問う敵**
- プレイヤーは護衛を注視しているため、画面外から来る鳥に気づけない
- 気づいて目で追い、旋回場所が確定し、buildSpotを探して押すまで、**最速でも数秒**かかる
- 旋回6秒のうち、実際に使えるのは**1秒程度**。見てから建てても落とせるのは1〜2体
- **見てから建てた効果は計算に入れなくてよい**

### 4-2. 鳥の被害計算

```
被害 ＝ (鳥の数 − 事前タワーが旋回中に落とせる数) × 12
normal1基は旋回6秒間で7体落とせる
```

検証: 鳥8体・normal1基（事前設置）→ 7体撃破・1体すり抜け・HP残90%。計算と一致。

### 4-3. 鳥の設計ルール

**① 単独で出す。地上の交戦と重ねない**

地上で交戦している最中はプレイヤーの目も指も塞がっており、画面外からの鳥に対応できない。**鳥の前後には空白を作る。**

副次的効果として、**鳥がステージのリズム（緩急）を強制する。**

**② 出す間隔は詰める（0.1秒程度）**

広げるとタワーが待ち時間なく処理できてしまう（2-2参照）。

**③ 旋回場所は固定する**

覚えれば次から事前に備えられる。**ランダムにしてはいけない**（永久に対処不能になる）。

**④ 出す数の上限＝護衛が丸ごと食らっても死なない数**

初見では必ず食らう前提のため、初見即死は避ける。

| 護衛 | HP | 上限 |
|---|---|---|
| dad | 120 | 10体 |
| mom | 90 | 7体 |
| son | 80 | 6体 |
| grandma | 70 | 5体 |
| cat | 60 | 5体 |

**⑤ 旋回点をタワーの射程外に置けば、旋回中は撃たれない**

旋回点とbuildSpotの距離関係が、そのまま鳥の難易度になる。

### 4-4. 鳥に必要な実装（未実装・要発注）

鳥は画面外から来るため、**予告なしでは成立しない**（気づけない敵に読みを問うことはできない）。

| 要素 | 役割 |
|---|---|
| 音 | 「来る」を伝える |
| 画面端の矢印 | 「どこか」を伝える。**鳥の現在位置を指す。旋回場所は示さない** |

矢印を出すタイミングが唯一の難易度ツマミになる（事前に備えていた人には無関係で、備えていなかった人の挽回幅を決める）。

## 8. Gから来る型（正面衝突）

ゴール方向から敵を出し、護衛に向かって突き進ませる型。キックボードのように
「すり抜けたら追走される」敵を、理不尽にせず脅威として使うための形。

### 8-1. なぜこの形なのか

trigger型で護衛の至近に速い敵を湧かせると、§2-6の2秒がまるごと効いて
プレイヤーの備えが無効化される。Gから出せばこれが解消する。

1. Gから護衛まで距離があるので、走ってくる間に2秒が消化される
2. **出る場所が固定されるので学習できる**（鳥の§4-3③と同じ理屈）。
   備えの成否が結果に直結する
3. 正面衝突なので、§4の発火逆算がほぼ要らない

### 8-2. Gに近い側のタワーは無意味

**護衛がそこまで来ないため、護衛範囲円の外で発動しない。**

実測（8体・normal 1基・護衛dad）:

| 構成 | 結果 |
|---|---|
| 1基 (10,3) | GAMEOVER |
| 2基 (8,3)(12,3) | CLEAR HP38% |
| 3基 (6,3)(10,3)(14,3) | **GAMEOVER** |

3基構成の (14,3) は一度も発砲せず、実質1基で戦っていた（結果が1基構成と
完全一致）。**基数を増やして弱くなる**ことが起こりうる。

**initial型とは要求される配置が違う。**

| | 求められる配置 |
|---|---|
| initial型 | その交戦地に届く「点」で解ける |
| Gから来る型 | 護衛と一緒に動ける「線」で解く（導線沿いに分散） |

同じ盤面で両方を問うと資源配分が対立するため、設計レバーとして使える。

### 8-3. 正解タワー位置の公式

記号:

| | 意味 |
|---|---|
| P | トリガー時の護衛位置(px) |
| D | 護衛からGまでの距離(px) |
| Ve | 護衛speed |
| Vz | 敵speed |
| n | 体数 |
| Δ | 出す間隔(秒) |

```
交戦開始点A ＝ P + Ve × (D − 85 + 2×Vz) ÷ (Ve+Vz) + 85
交戦終端点B ＝ P + Ve × (D − 450 + Vz×((n−1)×Δ + 2)) ÷ (Ve+Vz) + 450
　　　　　　　※Gを超えたらGの位置で頭打ち
正解タワー位置 ＝ (A + B) ÷ 2
```

Aは1体目が護衛に接触する地点、Bは最後の1体が護衛範囲円に入る地点。
その中点が交戦帯の中心になる。85はゾンビの攻撃が届く距離、450は護衛範囲円、
2×Vzは無敵2秒ぶんの遅れ。

**この式は「単一の最適点」ではなく「有効帯の中心」を出す。** 実用上は
1マスずれても効くため、そのほうが扱いやすい。

検証（stage_test_07・normal1基）:

| 敵 | speed | 予測 | 実測の有効帯 | 帯の中心 |
|---|---|---|---|---|
| キックボード | 90 | col9.7 | col8〜11 | col9.5 |
| サラリーマン | 50 | col11.5 | col10〜12 | col11 |

**敵speedが50と90の2種で、どちらも0.5マス以内で的中した。**

部品も個別に検証済み。「1体目が範囲円に入る時刻」＝
`(D − 450 + 2×Vz) ÷ (Ve+Vz)`。サラリーマンで15.5秒と計算され、
実測の初発砲は全パターン15550msで一致した。

### 8-4. 護衛がGから5マス以内では出さない（暫定・安全側の運用値）

> **確定ではない。** 3〜4マスは未測定で、実測は D=500 の1ケースのみ。
> 公式から「Bが盤面外に出る」ことは説明できるが、
> 境界の実値は2ケース目が取れるまで暫定とする。

| 護衛-G距離 | 何が問われるか |
|---|---|
| 19マス | 配置（正解から3マス外すとGAMEOVER） |
| 10マス | 配置（同上） |
| **5マス** | **配置（正解ならCLEAR、外せば削られる）** |
| 2マス | **何も問われない** |

2マスだと、タワーがあってもなくても結果がほぼ変わらない
（あり=HP残50%／なし=HP残25%、しかも両方CLEAR）。湧いた150ms後には
被弾が始まり、2秒の無敵すら消化されない。

**理不尽というより「無意味」——プレイヤーの判断が結果に反映されない。**

5マスが境界になる理由は公式で説明できる。D=500だとBの計算値がGを超え、
**盤面がもう足りない**状態になる。

3〜4マスは未測定のため、安全側に倒して**5マスを下限とする**。

8体・normal 1基での実測:

なお3体では間隔を変えても全部100%・CLOSE_CALL 0回で差が出なかった。
normal 1基が交戦時間2.6秒で処理できるのは3〜4体が上限のため、
**帯を見るには8体必要だった。**

### 8-6. 実ステージへの適用例

stage_test_06（18×18・3人リレー）のdadに適用した結果:

### 8-7. 体数の目標値は5体（実測・2026-07-29）

§8-6 の設計NG（CLOSE_CALL 0回）を解消するため、
専用の検証台 `stage_test_08`（20×6・まっすぐな道1本・
props/障害物ゼロ・dad単独・**キックボードのみ**）で体数を振った。

他の敵種を一切置いていないため、`[CLOSE_CALL_BY_SPAWN]` の内訳が
キックボード由来のものだけになる。

条件: G1=(18,3) から `atWpIdx:0`・間隔0.5秒・normal 1基を
公式の予測位置 (9,4) に設置。

| 体数 | HP残 | CLOSE_CALL | 被弾 | 最接近 |
|---|---|---|---|---|
| 8体 | 63% | 4回 | 3回 45dmg | 37px |
| 6体 | 88% | 2回 | 1回 15dmg | 81px |
| **5体** | **100%** | **1回** | **0回** | **144px** |

**5体が目標値。** HP100%を保ったままCLOSE_CALLが1回残り、
人格章の設計NG（0回）を回避できる。

内訳を見ると、5体構成では**最後の1体だけが144pxまで食い込み、
殴られる直前に落ちる**。「最後の1体が際どい」という形になるため、
プレイヤーの体感として緊張が残る。

**体数の坂は急である。** 8体→6体→5体で被弾が3回→1回→0回と動く。
2体の差で別物になるため、微調整のレバーとして扱いやすい反面、
安易に増やすと一気に崩れる。

#### 実ステージへの適用（stage_test_06・2026-07-29）

検証台で決めた5体を、そのまま stage_test_06 の dad seg3_shita に

## 9. Y（寄り道・定点防衛）

**この章の結論を先に書く: Yには §1〜§8 の計算式を使わない。**
それらは「護衛が動く」前提で組まれており、
護衛が静止するYでは説明力を失う。
Yには古典TDの漏らし計算を使う。

### 9-1. 既存の式がYで通用しないことの実測

検証台 `stage_test_10`（20×10・dad単独・本道に敵ゼロ・
`branchIdx:9`で(9,6)に着席・`waitTime:20000`・
`Y_R(19,6)`から正面1方向のみキックボードを流す・normal 1基(12,5)）。

**事前予測（外れた）**: 護衛が止まる＝speed 0 なので
交戦時間が `365÷90=4.06秒` と歩行時（`365÷140=2.61秒`）の
1.5倍に伸びる。よってY中はタワーが有利になる。

| 体数 | 歩行時(stage_test_08) | **Y中(stage_test_10)** |
|---|---|---|
| 5体 | HP100% CC1回 144px 被弾0 | HP100% CC1回 **142px** 被弾0 |
| 8体 | HP63% CC4回 37px 被弾3回45dmg | **HP38%** CC4回 87px **被弾5回75dmg** |

**5体では差が出ず、8体ではY中のほうが被害が1.7倍だった。**
「護衛が止まればタワーが有利」は成立しない。

### 9-2. 原因は同時攻撃

8体構成のログで、`t=38550ms` に**3体が同一時刻に殴っている**
（護衛HP 120→105→90→75）。`t=39600ms` でも2体同時。

**護衛が止まっていると、後続の敵が攻撃可能距離85pxに
横並びで到達して一斉に殴る。**

歩行時は護衛が前進して逃げるため、後続は自然に縦一列になり、
実質いちばん近い1体しか殴れない。
**「護衛が動いていること」自体が被弾を分散させる防御になっていた。**

5体で差が出なかったのは、タワーの連射（0.8秒）で処理が追いつき
列が滞留しないため。**滞留が起きた瞬間に同時攻撃が発生する。**

### 9-3. 最接近距離はYでは指標にならない

上表のとおり、**最接近距離はY中のほうが遠い（87px vs 37px）のに
被害は大きい。**

敵は攻撃可能距離85pxで足を止めてそこから殴るため、
静止した護衛にはそれ以上詰め寄らない。
**距離ではなく「同時に何体が攻撃圏にいるか」が被害を決める。**

CLOSE_CALLの最接近距離をYの安全度の指標に使わないこと。

### 9-4. Yの仕様（2026-07-29確定・小松判断）

上記を踏まえ、Yを以下の仕様とする。

**① Y中のゾンビは一撃殴ったら消える**

同時攻撃による青天井の被害を止め、被害の上限を確定させる。

```
Yの被害 ＝ (体数 − 落とせた数) × damage
```

これは §4-2 の鳥の被害計算と同じ形であり、
古典TDの「漏らした敵1体につきライフが1減る」とも同型である。

**② Y終了時に残敵は退場する**（実装済み: `retreatAll()`）

**①②により、Yは計算上「閉じた箱」になる。**
入った敵は必ずY内で決着し、Y後に持ち越さない。
残敵が本道に流れると以降の交戦地の計算が全て狂うため、
これがYを設計可能にする前提条件である。

**③ Y中の建設ロックを撤廃した（2026-07-29）**

旧仕様ではY中（着席から復路完了まで）の新規建設・アップグレードが
ブロックされていた。これを撤廃した。

**撤廃の理由**:
- ロックがあると、Yは「事前に全部建てて静観する」以外の
  遊び方が存在しない。プレイヤーの操作する余地がない
- `onDetourActivate` の中で `money += walletAmount` と
  `buildLocked = true` が同時に起きており、
  **着席時にもらった資金がもらった瞬間に使えなくなっていた**。
  1-4bのコメントには walletAmount:500 が
  「防衛タワー2〜3基分の想定」とあるが、Y防衛には使えなかった
- **ロックする理由がどこにも記録されていない**。
  v1.3以前の「Y＝静的TDモード」構想の名残と思われる
- spec05_game_identity.md「Yの役割」の整理（Yはノーマルタワー
  ディフェンスそのもの）に照らすと、リアルタイムに建て増しできる
  ことがジャンルとして本来の姿である

### 9-5. Yの地形（2026-07-29確定・小松判断）

**突き当りがY地点。突き当りを背にして ←↑→ の三方に
ゾンビルートがある。後方（護衛が来た分岐路）は封鎖する。**

**どのルートから来ても、Yの1つ手前のマスは1つだけ**——
三方が1マスの隘路に収束する砂時計型。

#### 後方封鎖の意味

**本道の遺産タワーが効かない。** Y専用の投資を強制できる。
着席時に資金が入る `walletAmount` の仕様と噛み合う。

#### 隘路の設計原則

**隘路は「必要だが足りない」ようにする。**

隘路1基は三方すべてをカバーできるため最も効率がよい。
しかし**隘路だけでは処理しきれない量を流す**ことで、
各枝の先にも配置させる。

成立条件:

```
総体数 ＞ 隘路に置ける基数 × 隘路1基の処理能力
隘路1基の処理能力 ＝ その地点での交戦時間 ÷ 撃破時間
```

これにより、問われるのは「どの方向を捨てるか」ではなく
**「隘路にいくら、枝にいくら配るか」**になる。
タワーの総数も増えるため、Y中は画面が派手になる。

#### 敵種の選び方

Y中の交戦時間は `365 ÷ 敵speed`（護衛speed=0のため）。

| 敵 | 交戦時間 | normal1基の処理能力 |
|---|---|---|
| キックボード(90) | 4.06秒 | 13体 |
| デブ(25) | 14.6秒 | **3.4体** |

**硬い敵ほど隘路だけでは足りなくなる。**
Yには警察・デブなど発数の多い敵が向く。
キックボードだけでは隘路一点置きで解けてしまう。

### 9-6. Yの禁止事項（§0.5に追加）

- **枝の長さはY地点から4.5マス以内に収める。**
  護衛範囲円450pxの外にいる敵はタワーが交戦対象にできないため、
  それより長い枝では上流で減らすことができない（1-4bで判明）
- **Y地点の周囲、各枝に届く位置にbuildSpotを置く。**
  Y中は建設ロックされ事前配置しか手がないため、
  枠が無ければ「見えているのに手が出せない」状態になる
  （§2-5 ルール3と同型）

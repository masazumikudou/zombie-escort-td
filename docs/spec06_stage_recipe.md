技術的な低レベルルール（prop衝突・PROP_DEFS・タワーコスト・シムCLI構文・旧文法の確定ステージ）は [spec05_stage_design.md](spec05_stage_design.md) を参照。本レシピはそれを前提にした新文法（区間制）専用の設計工程ガイド。

## 0. 設計の大原則（人格章からの継承）

- このゲームは「家族を読みで守り抜く、静かな脱出劇」。ステージの面白さの核は**読み**
- 見える脅威(initial)=初見の読み／見えない脅威(侵入)=周回の読み。三層(良/並/雑)は上達の時間軸
- 良=初見ほぼ不可能で正しい。並プレイ・強化ゼロでCLEAR成立がバランスの下限（Q2原則）
- 成立(三層)と面白さ(実機の体感)は別物。シムは壊れてないことの担保、面白さの最終判定は常に実機

## 1. 設計の順序（この順を崩さない）

1. **マップ・導線・交戦地**（小松担当）——道路網、護衛のpath、山場にしたい場所
1.5 **【新設】導線を引いた直後に猶予マップを計算する**（§4.6）——敵もタワーもまだ置かない。全spawn候補×全escortの猶予と最接近距離を算出し、余裕率3以上のゾーン（＝敵を置いても無駄な場所）と最接近250px超のspawn候補を除外する。導線とescort speedだけで完結するためベースMAP単位の資産として1回計算すれば再利用できる
2. **護衛の時刻表を作る**（§2）——全設計の座標軸。これを最初に作らないと以降が全部狂う
3. **区間を切る**——山場のまとまりごとに2〜4区間。区間ごとに面白さの仮説を1個持たせる（§6）
4. **脅威を配分する**（§3）——見える(initial)と見えない(侵入)の使い分け
5. **侵入の発火を逆算する**（§4）——時間計算。ここを怠ると敵は全員すり抜ける（実証済み）
6. **buildSpotsを引く**（§5）——道路沿い原則ぜんぶ。機械チェック必須
7. **タワー3人格パターンを組む**（§7）——良/並/雑
8. **シム三層＋CLOSE_CALL**——数字の確認
9. **実機**——面白さの判定。区間ごとに「何を感じたか」を聞く

## 2. 護衛の時刻表（全設計の座標軸）

護衛は決定論的に動く。pathの累積距離÷speedで、各waypointの通過時刻が確定する。

```
時刻(秒) = 累積距離(px) ÷ 護衛speed(px/s)
```

**stage_honban_testの実例**（dad speed50）: A(14,3)=28s / B(14,9)=40s / C(3,9)=62s / D(3,15)=74s / ゴール=106s

この表が「動かせない時刻表」。敵・タワー・演出のすべてはこの時刻表に合わせて設計する。計算はPythonスクリプト（cum距離の積算）で機械化済み——R-6の検証スクリプトに統合予定。

## 3. 脅威の使い分けの法則

| | initial（見える脅威） | 盤外侵入（見えない脅威） |
|---|---|---|
| 時間計算 | **不要**（最初からそこにいる） | **必須**（§4） |
| 読み | 初見から読める（観察） | 周回で読める（記憶） |
| 配置の自由度 | 高い。導線のどこでも | 低い。交戦地から近い盤外限定 |
| 難易度レバー | 導線への近さ×数 | 数×発火密度 |

**法則1: 交戦地から遠い脅威はinitialで置け。** 盤外から鈍足(30px/s)で長距離を歩かせる設計は時間的に破綻する（§9地雷3）。盤外侵入のスポーン地点は目安として**交戦地から5セル以内の盤外**。

**法則2: 追わせるな、向かわせろ。** leash待ち伏せは精密な時間逆算が必須で壊れやすい。**護衛の進行方向の前方から来る敵（直接追跡・正面衝突）は閉速度=護衛speed+敵speed で必ず出会う**ため、時間設計がほぼ不要。侵入の基本形は正面衝突、leashは交戦地至近の盤外からの短距離に限る。

**法則3: 背後からの追走は永遠に追いつかない。** 敵speed(30) < 護衛speed(50)。護衛が通過した後に後方から出す敵は、直接追跡では絶対に接触しない。出すならleashで先回りさせるしかなく、それには法則1の距離制限がかかる。

## 4. 侵入の発火逆算（必須計算）

```
敵到達時刻 = 発火時刻 + 盤外歩行時間 + 盤内歩行時間
           = 護衛が発火wpを通過する時刻 + (スポーン地点から交戦地までの距離 ÷ 敵speed)
成立条件: 敵到達時刻 ≦ 護衛到達時刻 - マージン(2〜4秒推奨)
```

- マージンは「敵が先に着いて待ち構える」余裕。0だとすれ違いギリギリで不安定
- **盤外部分の歩行時間を忘れるな**（盤外2セル=200px=6.7秒。§9地雷5）
- 正面衝突型（法則2）はこの計算が不要。会合点だけ概算しておく: 会合時間 = 初期距離 ÷ (護衛speed+敵speed)
- 発火wpは必ず**自区間のrange内**に収める。範囲外のatWpIdxは発火しない（現実装。区間またぎ予約発火は未実装——必要になったらCCに依頼、ただし正面衝突型で大半は回避可能）

## 4.5 タワー処理速度と護衛通過時間のせめぎ合い

§4は「敵が護衛に届くタイミング」の計算だった。ここでは「タワーが敵を倒しきるタイミング」を同じ時間軸に乗せる。1基のタワーが複数体を直列処理する交戦地（増援・逆走など)では、この2つの時計算がせめぎ合う。

```
1体撃破時間 = ceil(敵HP ÷ タワーdmg) × タワー連射間隔
複数体処理の限界 = (1体撃破時間 × 体数) ≦ (敵の初期距離 ÷ 敵speed) − 護衛への到達猶予
```

**重要**: 敵の初期距離÷敵speedの右辺は、護衛のspeed・HPに依存しない。一方「護衛への到達猶予」は護衛の通過タイミングに依存し、護衛speedが変わればトリガーからの経過時間そのものが変わる。escortごとに護衛speed/HPが異なる場合（dad/mom/他家族）、この式は同じ座標・同じタワー構成であっても解が変わる（§9地雷13参照）。

**実例（stage_honban_test dad区間・2026-07-19）**: 交戦地E'でnormal@(15,16)がid15/16の2体を直列処理する際、trigger intervalが1200msだと2体目の接近が撃破完了前に間に合い護衛が10dmg被弾した。intervalを4500msまで伸ばして初期距離を稼ぎ、複数体処理の限界式を満たすことで護衛被弾ゼロ・HP100%クリアを達成した。

**教訓**: タワーを密着させて重ねる対処（隣接建設）は、ターゲット重複により同一個体に無駄撃ちが発生し、他個体を無防備にする逆効果を生むことがある（実例: normal@(12,4)→(16,4)移動でHP83%→58%に悪化）。処理速度が足りない場合は「タワーを増やす／近づける」より先に、上式に基づいて「敵の到達を遅らせる（trigger位置・interval調整）」を検討すること。

## 4.6 タワーがもらえる時間（交戦猶予）

§4.5は「敵が護衛に届くか」の計算だった。ここではタワーが何秒もらえるかを計算する。三層検証が成立しても緊張が生まれない場合、原因はほぼここにある。

**なぜズレるのか**: 護衛範囲円（450px）は直線距離で判定する。一方、護衛は道に沿って歩く。この2つが一致しない場所——曲がり角の向こう、Uターンの先——では、タワーが撃ち始めてから護衛が到着するまでに大きな空白ができる。

```
猶予(秒) = 護衛が敵に最接近する時刻 − 敵が範囲円に入った時刻
所要(秒) = ceil(敵HP ÷ タワーdmg) × 連射間隔 × 体数
余裕率  = 猶予 ÷ 所要
```

**判定の目安**（※実機照合前の仮当て）:

| 余裕率 | 状態 |
|---|---|
| 3以上 | 緊張ゼロ確定。護衛が着く前に全滅している |
| 1.0〜1.5 | ギリギリ帯（目標） |
| 1.0未満 | 被弾確定 |

最接近距離が250pxを超えるspawnは、敵として無効（撃たれるだけで護衛に触れられない案山子）。配置前にこの判定で除外すること。

**実測例1: ステージ1（15×10・H字）**: dad speed50。seg1のinitial 2体は範囲円に入るのが t=4s / 8s、護衛の到着は t=16s / 20s。猶予12秒に対しサラリーマン1体の所要は1.6秒。余裕率7.5。結果はHP100%クリア・CLOSE_CALL 0回。「配置が良かった」のではなく、構造的に緊張が発生し得なかった。

**実測例2: ステージ20プロトタイプ（1-7・30×20）**: seg4のinitial（F1〜F4のデブ4体）の猶予は、dad基準で 32秒 / 60秒 / 92秒 / 120秒。デブ1体の所要は約5秒。余裕率6〜24。原因は導線の形。row12を左端まで走破する間、row16のF1〜F4がずっと範囲円内に入り続ける。クライマックスとして設計された区間が、幾何学的に緊張を作れない状態だった。

**護衛speedとの関係**: 猶予は護衛speedに反比例する。遅い護衛ほど全spawnで猶予が長い。1-7の全24spawn×5家族を計算した結果、grandma（speed35）は全spawnで猶予が最大であり、被ダメージ0という実測と一致した。被ダメージの順位（cat55 > son45 > dad27 > mom15 > grandma0）も、おおむね猶予の短い順に並ぶ。「遅い護衛は易しい」の正体はこの猶予である。

**猶予で説明できないこと**: 1-7で被弾が集中した2箇所（E_R / R_R）の猶予は中位だった。ここが危険だった理由はカバーするタワーが1〜2基しかなかったことであり、幾何ではなく配置の問題。**猶予は「どの家族が苦戦するか」を説明するが、「どこで被弾するか」は説明しない。**前者は導線の問題、後者はbuildSpotと配置の問題として切り分けること。

**この計算は導線とescort speedだけで完結するため、敵配置・タワー配置に一切依存しない。** ベースMAP単位の資産として1回計算すれば、そのMAPから派生する全ステージで再利用できる。R-6（validate_stage.js）に実装すべき機能の筆頭。

**未確定事項**:
- 余裕率の閾値（3 / 1.0〜1.5）は机上の仮当て。実機で「どの余裕率だとギリギリに感じるか」を照合して確定させること
- 猶予は最接近点1点で計算しているが、実際には護衛が範囲円内にいる全区間で交戦が起きる。より精密には「交戦可能時間の総和」で測るべきかもしれない（未検討）

## 5. buildSpots設計

- **方針: 道路沿いの空き地は原則ぜんぶspot。** 選択肢の多さ=迷い=読みゲーの本体。少ないspotは答えを配っているのと同じで、「下手な配置」が存在できない
- 除外: propの**フットプリント**（登録座標だけでなく3×3等の足元全域。§9地雷6）、道路セル、グリッド外
- 間引き: 過度な隣接連鎖はタッチ誤爆リスク（正式ルールは2-5の実機タップ検証後）
- **山場を作る前に、そこに届くspotがあるか確認**（punchの射程100px問題、seg4右半分ノーカバー問題の教訓)
- 難易度レバー: Lv1はspot少なめ（迷わせない=チュートリアル）、Lv上昇で増やす
- 検証は機械チェック必須（R-6スクリプト）。目視は26%の衝突を見逃した実績がある

## 6. 区間設計と面白さの仮説

- 1区間=1つの面白さ仮説。stage_honban_testの実例: seg1=読み→増援 / seg2=緩の対照群 / seg3=不気味な静寂 / seg4=挟撃クライマックス / mom区間=キャスト入れ替え
- 仮説を区間に分離しておくと、実機の感想が「どの仮説が当たったか」の実験結果になる（1ステージ=5実験）
- 緩急: 全区間を賑やかにすると緩急が死ぬ。意図的な「緩」区間を入れ、実機で「心地よい息継ぎ」か「退屈」かを判定
- 区間境界のretreat（残敵の画面外退場）が失敗の蓄積を切る。区間内で解決させたい敵はその区間に置く

## 7. タワー3人格パターン（三層検証の組み方）

三層は難易度の層ではなく**プレイヤー像の層**。全パターン900G基準（予算は同額、使い方だけ変える）：

| 層 | 人格 | 組み方 | 期待される破綻 |
|---|---|---|---|
| 良 | 読み切る人 | 全区間に配分。各交戦地に届く最良spotを吟味 | 破綻しない（CLOSE_CALLは出る=ギリギリ） |
| 並 | 反応する人 | **前半の交戦地に過剰投入（同じ場所に2〜3基）、後半スカスカ** | 終盤の資金枯渇でじわじわ削られる |
| 雑 | 釣られる人 | 900G使い切るが、ice散財・交戦地から遠い「イメージ買い」・自陣固め | 序盤〜中盤で崩壊（ただし§9地雷7参照） |

**判定基準【v2改訂・2026-08-16・小松判断】**: **良＝HP100%クリア可能な配置の存在証明が唯一の絶対条件**。「置き方によらずステージ自体にその性質があるか」だけを見る——存在するかしないかの二値なので、プレイヤーの配置の巧拙に依存しない。100%に必要なタワー総額はタイトさの物差しとして引き続き記録する。

**雑100%不成立・並・Lv別目標帯は合否判定から外す（実施は任意・参考記録のみ）**。以下、旧運用の破棄理由を記録として残す:
- **雑検証の限界**: Claudeが組める「雑」は正解を知った上でわざと外した配置であり、初見プレイヤーの実際の外し方ではない。実機（小松プレイ）はClaudeが想定した雑パターンのどれとも似ておらず、検証として機能しなかった（外周ぐるり・確定ABAステージ双方で確認）。また「資金が余っているのにタワーを建てない」型の雑はプレイヤーが取らない行動であり、そもそも検証として成立しない
- 難易度の数値定義（「良100%−雑スコア」の差分）も上記に伴い運用を終了。難易度は小松の実機プレイでの相対順位づけに一本化する（工程表2-2参照）

**CLOSE_CALLの目安は撤回**（旧: 0回=楽勝すぎNG / 3〜10回=ノーダメギリギリ目標帯 / 20回超=修羅場すぎ）。0回=設計NGという運用を破棄した理由: **配置が上手いときにも0回になる**——外周ぐるりの良100%配置（タワーを敵の湧く場所の真横に固めた構成）はCLOSE_CALL 0回でHP100%クリアだったが、同ステージの小松実機プレイでは8回/7箇所発生している。スカスカなステージを弾く目的で導入した指標が、逆に「上手い配置」も弾いてしまうことが実測で判明したため。CLOSE_CALLは以後、**良い配置ができたときの緊張度を見る参考値**として記録は続けるが、合否判定には一切使わない。

## 8. 実機照合の聞き方

実機後の質問は「面白かった?」ではなく**「各区間で何を感じたか、一言ずつ」**。区間=仮説なので、答えがそのまま実験結果になる。シムのCLOSE_CALL分布と突き合わせ、「数字と体感の対応表」（§10）に1行追加する。

## 9. 踏んだ地雷集（すべて実話・2026-07-17〜18）

1. **initialの書式**: `{col,row,enemy}`直書きは**黙殺される**（エラーなし）。正: spawns辞書に名前付き地点を登録し`{spawn:"名前",enemy:{...}}`で参照。triggersと同形式
2. **leashToの位置**: 必ずenemyオブジェクトの**中**。外（トリガー直下）に置くと黙殺
3. **時間計算を忘れると全員すり抜ける**: 初版は5トリガー中5個が「敵到達>護衛到達」で、9体全員が交戦ゼロのすり抜け。§4の計算を必ず行う
4. **区間範囲外のatWpIdxは発火しない**: 前倒しした発火wpが自区間のfromWpより手前に出たら、正面衝突型への転換を検討（区間またぎ発火は未実装）
5. **盤外歩行時間の計上漏れ**: 盤外2セル分=6.7秒。地味に効く
6. **propはフットプリントで避ける**: 登録座標1セルだけ見て除外した結果、42spot中11箇所(26%)がめり込んだ。機械チェック必須
7. **buildSpotが多い盤面では雑配置も偶然当たる**: 雑パターンが偶然initial の真横に建って粘った実例あり。雑を組むときは「交戦地の近くに建てない」を意識的に。逆にこれは盤面の健全さ（どこに建てても多少は機能する）の証明でもある
8. **「シムが通る」と「実機の絵が正しい」は別**: カメラ拡張で虚無が見えた件、墓デカール自動追従の件。絵の要件はコードの理屈で先回りできない。毎回実機で見る
9. **同期漏れは全てを無に帰す**: npm run syncを忘れると実機は旧コードのまま動き続け、「実装したのに変わらない」の調査で半日消える。実機確認前のsyncをルーチン化
10. **予約発火は不可能・トリガーは交戦させたい区間に置く**: 「区間の最後のwpで発火→次区間で交戦」は構造的に成立しない。区間離脱時のretreat/pendingクリアに猶予がなく、発火直後（次wp到達=最短2秒）に敵が強制退場する。seg3の敵を3回連続で消し飛ばした実話。トリガーは必ず交戦を起こしたい区間そのものの範囲内(fromWp〜toWp)に置く
11. **leash待ち伏せは正面衝突を作れない**: leashで交戦地に足止めした敵は、待ち伏せ地点で護衛とすれ違った後、起動して護衛を追う=背後からの追走=永遠に追いつかない(法則3)。正面衝突を狙うなら**leashを外した直接追跡**で、敵を護衛の進行方向の逆側から出す(下降路なら下から、直進路なら前方から)
12. **タワー配置の入力書式とログ表示形式の混同**: run_sim.jsの入力書式は `type:col,row[@ms]`（コロン+カンマ、括弧なし。正規表現`^(\w+):(\d+),(\d+)(?:@(\d+))?$`）。一方[BUILD]ログの出力表示は`type@(col,row)`形式（`@`+括弧）で人間向けに整形されている。この2つを混同して出力形式のまま再入力すると、パーサーに一致せずタワーが1基も配置されないまま（[BUILD]行皆無）シムが実行され、原因不明のGAMEOVERを引き起こす。入力欄には常に`type:col,row[@ms]`形式を使うこと。
13. **タワー配置はescortごとに個別に解く必要がある（レシピ化できない）**: §4.5の式は汎用化できるが、式の右辺（護衛への到達猶予）は護衛speed・HPに依存するため、「良100%配置」はescort単位の解であり使い回せない。dad(speed50/HP120)で確定した100%配置を、mom(speed65/HP90)にそのまま適用すると、同じタワー構成でも護衛の通過が速くタワーの処理猶予が減るため100%を割る可能性が高い（未検証・理論上の予測）。3人目以降の家族が追加された場合も同様。ステージのタワー配置レシピはescortごとに§4.5の式を再計算して個別に確定させること。
14. **enemyのhp明示指定はbalance.jsonを無条件で上書きする**: ステージJSONの`enemy`オブジェクトに`hp`を直接書くと、`_buildEnemyDef`の仕様上balance.json側の種別ごとの値より常に優先される（`if (def.hp !== undefined) result.hp = def.hp;`）。balance.jsonでバランス調整をしても、hpを明示指定しているステージには一切反映されない——「敵を弱くしたのに変わらない」の典型的な原因になる（2026-07-26発覚、既存6ステージ全123箇所が該当）。**ルール: 新規ステージJSONのenemyにhpを書かない（balance.json値を継承させる）。意図的に個体を強化・弱体化したい場合のみ明示指定を許可し、その際は必ず`_comment`で理由を残すこと**（例: `"_comment": "seg4クライマックス用に強化。通常個体の1.5倍"`）。
15. triggerとinitialのspawn名がspawnsに未定義でも、警告なくスキップされる（2026-07-28にSpawnEventManager.jsへconsole.warnを追加して解消済み）。症状は「[SPAWN]が1行も出ず、スポーン総数だけが減る」。原因を区間やatWpIdxの側に求めると迷走する。なお"GOAL"という名前は正しく定義しても発火しない事象が確認されており、使用を避けること。
